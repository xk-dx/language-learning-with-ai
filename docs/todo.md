## AI 配置页技术债

### 当前状态

当前前端已经有“系统设置 → 大模型配置 / 图片服务配置”，也在快速上手导览第二步中提供基础配置入口。

已完成：

- 提供 API Key、Base URL、默认模型、Pexels Key 的表单。
- 将用户填写的内容保存到浏览器 `localStorage`，key 为 `wordforge-user-settings-v1`。
- 提供“测试连接”按钮，请求 `GET http://localhost:5001/api/config`，用于确认 Flask 后端是否在线，并展示后端当前读取到的模型和服务地址。

未完成：

- 前端填写的 API Key 不会传给后端。
- 前端填写的 Base URL 不会改变后端实际使用的模型服务。
- 前端填写的默认模型不会改变 Flask 调用 AI 时的模型。
- 前端填写的 Pexels Key 不会改变后端图片搜索接口使用的 Key。

真实 AI 调用仍然由后端启动时读取的环境变量决定：

```text
backend_flask/.env
OPENAI_API_KEY / DEEPSEEK_API_KEY
OPENAI_BASE_URL
DEFAULT_MODEL
PEXELS_API_KEY
```

因此当前状态可以定义为：

```text
AI 配置页 = 交互原型 + 本地保存 + 后端连接检测
真实 AI 调用配置 = backend_flask/.env
```

### 为什么当前阶段可以接受

这个项目是 HCI 课程大作业，当前重点是前端交互流程、信息架构和用户心智模型，而不是完整的后端配置管理系统。

对于 HCI 展示来说，现在的配置页已经具备足够的交互价值：

- 用户知道 AI 能力需要配置，不会觉得功能凭空失败。
- 用户能看到一个符合真实 AI 产品习惯的配置入口。
- 用户可以通过“测试连接”确认本地 Flask 服务是否在线。
- 页面给后续真实配置系统预留了清晰位置。
- 避免为了课程展示把 API Key 直接写入前端或引入不必要的安全复杂度。

汇报时可使用类似表述：

```text
系统设置页提供了 AI 配置入口和后端连接检测。当前 Demo 环境中真实模型配置仍由本地 Flask .env 管理，以避免在前端暴露密钥；前端配置表单作为用户侧配置界面的交互原型保留。
```

### 如果后续要做成真实配置系统

可以考虑新增后端接口：

```text
GET  /api/runtime-config
POST /api/runtime-config
POST /api/test-config
```

最小实现方案：

1. 后端新增本地配置文件，例如：

   ```text
   backend_flask/data/runtime_config.json
   ```

2. 前端设置页提交 API Key、Base URL、默认模型、Pexels Key 到 `POST /api/runtime-config`。

3. 后端 AI 请求时优先读取 runtime config；如果为空，再回退到 `.env`。

4. “测试连接”改为 `POST /api/test-config`，用用户当前填写的配置临时创建 OpenAI-compatible client，并发起一次轻量请求。

实现时需要注意：

- API Key 会明文保存在本地文件。虽然本地 Demo 可以接受，但需要在说明里注明。
- 当前后端 `client = OpenAI(...)` 是模块加载时初始化的；如果支持运行时修改配置，需要改为每次请求时按当前配置创建 client，或在配置更新后重新创建 client。
- Pexels Key 也需要纳入同一套运行时配置，否则图片搜索仍会只读 `.env`。
- 需要提供“恢复为 .env 默认配置”或“清空本地配置”的操作。
- 需要处理配置无效、后端未启动、Key 缺失、模型不可用等错误状态。

## 完成标准建议

每完成一轮流程重构，至少确认：

- 页面入口是否符合 `docs/re-organize.md` 的流程归位。
- 原有核心功能是否仍可访问。
- 是否减少了“技术功能堆叠”的感觉。
- 是否能用一句用户任务描述解释该页面存在的原因。
- `npx.cmd vite build` 能通过。
